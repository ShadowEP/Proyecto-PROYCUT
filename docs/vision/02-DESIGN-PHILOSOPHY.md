02-DESIGN-PHILOSOPHY.md
Filosofía de Diseño de ProyCut
"La mejor interfaz es aquella que desaparece y permite que el usuario piense únicamente en su trabajo."

Introducción
El diseño de ProyCut no tiene como objetivo verse moderno.
Tiene como objetivo ayudar a las personas a trabajar mejor.
Cada pantalla, cada botón, cada mensaje y cada interacción deben reducir la carga mental del usuario.
No diseñamos para impresionar.
Diseñamos para que el trabajo fluya.
Cuando el usuario deja de pensar en el software y se concentra en fabricar, el diseño ha cumplido su propósito.

Primer Principio
La simplicidad es una responsabilidad.
La simplicidad no significa tener menos funciones.
Significa presentar la complejidad en el momento adecuado.
El usuario nunca debe sentirse abrumado.
La información aparecerá únicamente cuando aporte valor.

Segundo Principio
El software debe pensar antes que el usuario.
Siempre que sea posible, ProyCut debe anticiparse.
Debe recordar.
Debe sugerir.
Debe completar.
Debe prevenir errores.
Nunca debe esperar que el usuario haga trabajo que el sistema puede hacer automáticamente.

Tercer Principio
La interfaz debe contar una historia.
Cada pantalla responde tres preguntas:
¿Dónde estoy?
¿Qué puedo hacer aquí?
¿Cuál es el siguiente paso?
El usuario nunca debe sentirse perdido.

Cuarto Principio
Un clic debe tener consecuencias.
Cada acción debe generar una respuesta clara.
Guardar.
Calcular.
Optimizar.
Exportar.
Imprimir.
Visualizar.
El sistema siempre debe comunicar qué ocurrió y qué sigue.

Quinto Principio
La información importante siempre tiene prioridad.
El costo.
El desperdicio.
La rentabilidad.
Los materiales.
Las alertas.
Nunca deben competir visualmente con elementos secundarios.
La interfaz debe dirigir la atención del usuario hacia lo que realmente importa.

Sexto Principio
La confianza también se diseña.
Un cálculo debe poder explicarse.
Un resultado debe poder verificarse.
Un error debe poder comprenderse.
El usuario debe saber de dónde proviene la información.
No queremos una "caja negra".
Queremos transparencia.

Séptimo Principio
Los errores deben enseñar.
Cuando algo salga mal, ProyCut nunca mostrará un mensaje como:
"Error 504".
En su lugar explicará:
Qué ocurrió.
Por qué ocurrió.
Cómo resolverlo.
Y, cuando sea posible, ofrecerá una solución inmediata.

Octavo Principio
El aprendizaje debe ser natural.
El usuario no debería necesitar un curso para utilizar ProyCut.
El sistema enseñará mientras se utiliza.
Mediante:
	•	sugerencias;
	•	ejemplos;
	•	recomendaciones;
	•	ayudas contextuales;
	•	explicaciones sencillas.

Noveno Principio
La consistencia genera confianza.
Un botón debe comportarse igual en todo el sistema.
Los colores deben significar siempre lo mismo.
Los iconos deben tener un único significado.
Las acciones similares deben verse iguales.
La coherencia reduce la necesidad de pensar.

Décimo Principio
El diseño nunca termina.
Cada pantalla deberá evolucionar.
Cada versión deberá simplificar.
Cada mejora deberá reducir pasos.
Nunca consideraremos una interfaz "terminada".
Siempre podrá hacerse más clara.

La personalidad visual de ProyCut
ProyCut debe sentirse como una persona.
No como un programa.
Debe transmitir:
Honestidad
Nunca exagera.
Nunca oculta.
Siempre explica.

Cercanía
Habla como una persona.
No como un manual técnico.

Inteligencia
Anticipa necesidades.
Hace recomendaciones útiles.
Nunca presume su capacidad.

Precisión
Cada dato inspira confianza.
Nada se muestra sin propósito.

Optimismo
Celebramos los logros.
Motivamos el progreso.
Acompañamos al usuario.
Sin exageraciones.
Con autenticidad.

La Regla de Oro del Diseño
Antes de aprobar cualquier pantalla, cualquier miembro del equipo deberá responder:
	1	¿Es más simple que la versión anterior?
	2	¿Reduce la incertidumbre?
	3	¿Ahorra tiempo?
	4	¿Puede entenderla un usuario nuevo?
	5	¿Genera confianza?
	6	¿Se siente como ProyCut?
Si una sola respuesta es no, el diseño aún no está listo.

El Test ProyCut
Cada nueva función, pantalla o idea debe pasar el Test ProyCut.
El Test ProyCut (10 preguntas)
Antes de aprobar cualquier cambio, pregúntate:
	1	¿Resuelve un problema real?
	2	¿Reduce la incertidumbre del usuario?
	3	¿Hace el trabajo más rápido?
	4	¿Hace el trabajo más sencillo?
	5	¿Genera confianza?
	6	¿Respeta nuestra filosofía?
	7	¿Puede entenderlo un usuario sin capacitación?
	8	¿Evita errores antes de que ocurran?
	9	¿Seguirá siendo útil dentro de cinco años?
	10	¿Hace que ProyCut sea más ProyCut?
Si la respuesta a la última pregunta es no, probablemente la función no pertenece al producto.
